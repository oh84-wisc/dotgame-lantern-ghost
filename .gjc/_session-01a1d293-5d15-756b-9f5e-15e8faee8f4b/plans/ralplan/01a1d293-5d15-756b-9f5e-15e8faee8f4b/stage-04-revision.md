**Viable Options**

## 2. 레이아웃 2·3 (goal-4)

### 2.1 설계 규칙
- 규격 20열 × 15행, 바깥 테두리 `#`.
- 촛불 수: 레이아웃 2 = 14, 레이아웃 3 = 16 (스펙 R2 범위 10~20).
- 순찰 고리: 레이아웃 2 = 10칸, 레이아웃 3 = 12칸 (스펙 R13 범위 8~12). 고리 칸은 모두 바닥이며 연속 칸은 상하좌우로 인접하고 마지막 칸은 첫 칸과 인접하다.
- `G` 칸 = 고리 첫 칸 (index 0). `S`는 고리에 들어가지 않는다.
- 모든 촛불은 `S`에서 벽을 피해 걸어서 닿을 수 있다.

### 2.2 검증 상태 [R1-2, R1-5]
- 손으로 확인한 것 (재현 가능): 행 길이, 촛불 개수, 고리 길이, 고리 인접, G = 고리 첫 칸, 촛불 도달 가능성. 위 2.1 규칙은 사람이 기획서 5장 원문과 대조해 확인한다.
- 승리 가능성: 에이전트가 판정 순서 1~9를 따르는 완전 탐색으로 계산했다 (레이아웃 1 = 85, 레이아웃 2 = 91, 레이아웃 3 = 80 최단 턴). 이 값은 저장소에 재현 스크립트가 없는 미검증 주장이다. 기획서에 숫자를 넣지 않는다. 승리 가능성은 AC-4.9로 사람이 확인한다. [R2-3a]
- 키 한 번 120 ms 잠금이므로 최단 경로는 입력만 약 10 s 이상이다. 60초 안에 사람이 깰 수 있는지가 실제 위험이다 (8장).

### 3.2 최고 점수 저장 [R1-3, R1-6]
- localStorage 키 1개: `lantern-ghost.highScore`. 값은 정수 문자열.
- 순수 함수 (src/score.js, `node --test`로 테스트):
  - `parseHighScore(raw)`: `raw`가 `null`, 빈 문자열, 정수가 아닌 값이면 0. 정수 문자열이면 그 정수.
  - `nextHighScore(stored, score)`: `max(stored, score)`.
- 얇은 저장 래퍼 `readHighScore()` / `writeHighScore(value)` (src/score.js 안, 테스트 대상 아님): `localStorage` 접근이 예외를 던지면 0을 읽고, 쓰기는 건너뛴다.
- 저장 규칙 [R1-3]: 판이 끝날 때 (승리 또는 패배, 점수 0 포함) 항상 `writeHighScore(nextHighScore(readHighScore(), score))`를 호출한다. 그래서 첫 판이 끝나면 키가 생긴다.

- AC-3.2, AC-3.5, AC-3.7: 변경 없음.
- AC-2.1 ~ AC-2.5, AC-2.7, AC-1.x: 레이아웃 1 기준 문장이다. 변경 없음. 9장 머리말에 "AC-1.x ~ AC-3.x는 레이아웃 1 기준이다 (goal-4 이후에도 레이아웃 1에서 동작해야 한다)" 한 줄을 추가.

## 6. 테스트 기대값 (기획서 숫자에서만 가져옴)

- 레이아웃 3개, 촛불 12 / 14 / 16, `TOTAL_CANDLES` = 42.
- 순찰 고리 길이 8 / 10 / 12. 고리 칸은 모두 벽이 아니고 연속 칸은 인접하며 마지막 칸은 첫 칸과 인접.
- `G` 칸 = 고리 첫 칸. `S` 칸은 고리에 없다.
- 레이아웃 1 클리어 → `layoutIndex` 1, `timeLeftMs` 60000, `screen` `playing`, `runScore` 12.
- 레이아웃 3 클리어 → `screen` `win`, `runScore` 42.
- 패배 시 `runScore` = 이전 레이아웃 합 + 현재 켜진 수.
- `parseHighScore(null)` = 0, `parseHighScore("")` = 0, `parseHighScore("abc")` = 0, `parseHighScore("17")` = 17.
- `nextHighScore(0, 0)` = 0, `nextHighScore(42, 17)` = 42, `nextHighScore(17, 42)` = 42.

## 7. 수용 기준 (9장, 사람 브라우저 확인, 번호 체계 AC-x.y)

**goal-4 (레이아웃 2·3)**
- AC-4.1: 레이아웃 1을 클리어하면 중간 화면 없이 레이아웃 2가 바로 나온다. HUD에 `켜진 촛불 12/42`, 타이머가 60초로 다시 줄어든다. 유령은 열 1 행 2에서 시작한다.
- AC-4.2: 레이아웃 2에서 경비병이 기획서 5장 레이아웃 2 순찰 고리 (10칸)를 따라 돈다. 유효한 이동 10턴 뒤 경비병이 `G` 칸 (열 12 행 13)에 돌아온다. 벽에 막힌 방향키는 경비병을 움직이지 않는다.
- AC-4.3: 레이아웃 2의 촛불 14개를 모두 밟으면 레이아웃 3이 바로 나온다 (최종 화면 아님). HUD에 `켜진 촛불 26/42`.
- AC-4.4: 레이아웃 3에서 경비병이 기획서 5장 레이아웃 3 순찰 고리 (12칸)를 따라 돈다. 유효한 이동 12턴 뒤 경비병이 `G` 칸 (열 10 행 12)에 돌아온다.
- AC-4.5: 레이아웃 2·3에서 경비병 시야 칸으로 움직이거나 경비병 칸으로 들어가면 즉시 패배 화면이 뜨고 `켜진 촛불 N/42`가 있다. N = 이전 레이아웃 합 + 현재 켜진 수.
- AC-4.6: 레이아웃 3의 촛불 16개를 모두 밟으면 최종 화면이 뜬다. `총 켜진 촛불 42/42`가 있다.
- AC-4.7: 패배 또는 승리 화면의 [다시 시작]을 누르면 레이아웃 1로 돌아가고 `켜진 촛불 0/42`, 타이머 60, 유령 열 1 행 2, 경비병 열 9 행 14. [처음으로]는 시작 화면.
- AC-4.8: 레이아웃 2 또는 3에서 타이머를 60초까지 두면 패배 화면이 뜨고 `켜진 촛불 N/42`가 있다. 타이머는 0에서 멈춘다.
- AC-4.9: 레이아웃 3를 60초 안에 깰 수 있다 (사람 플레이 확인). 기획서에 최단 턴 수를 적지 않는다. 깰 수 없으면 기획서를 먼저 고친다 (AGENTS.md).

**goal-5 (사운드·최고 점수·최종 화면)**
- AC-5.1: [시작] 클릭 후 촛불을 밟으면 짧은 소리가 난다. 개발자도구 Network 탭에 오디오·이미지·폰트 파일 요청이 0개다 (`.js` 모듈 요청과 브라우저가 자동으로 요청하는 `favicon.ico`는 제외).
- AC-5.2: 레이아웃 1·2 클리어 시 상승음, 패배 시 하강음, 최종 승리 시 3음 상승음이 난다. 소리 끄기 버튼이 없다.
- AC-5.3: 첫 판이 끝나면 (점수 0이라도) 개발자도구 Application > Local Storage에 키 `lantern-ghost.highScore` 1개가 생기고 값은 정수 문자열이다. 다른 키는 생기지 않는다.
- AC-5.4: 첫 판: 레이아웃 1을 클리어한 뒤 레이아웃 2에서 촛불을 켜지 않은 채 패배한다 (점수 12). 새로고침한다. 둘째 판: 레이아웃 1에서 촛불을 켜지 않은 채 패배한다 (점수 0). 둘째 판의 패배 화면 `최고 점수`가 12다. (레이아웃 1에서 12개를 모두 켠 패배는 불가능하다: 12번째 촛불이 클리어를 일으키므로 레이아웃 1 패배 최대는 11이다. [R2-1])
- AC-5.5: 최종 화면에 `총 켜진 촛불 42/42`, `최고 점수 M`, [다시 시작], [처음으로] 4개가 있다. [처음으로]는 시작 화면, [다시 시작]은 레이아웃 1로 간다.
- AC-5.6: 화면 색은 기획서 6장 8색 hex만 쓴다 (사람이 hex를 `src/sprites.js`와 대조).
- AC-5.7: 외부 이미지·오디오·폰트 파일 요청이 0개다 (웹폰트 1개 예외는 쓰지 않는다).
- AC-5.8: 레이아웃 3 클리어 후 [다시 시작]을 누르면 최고 점수는 그대로 42이고 `켜진 촛불 0/42`로 시작한다.

## 8. 위험과 열린 질문

- 레이아웃 3는 60초 안에 깰 수 있는지 사람이 확인해야 한다 (AC-4.9). 실패하면 숫자를 바꾸지 않고 기획서를 먼저 고친다.
- AGENTS.md "좌표를 따로 적지 않는다"와 순찰 고리 좌표 표기가 충돌한다. 기존 레이아웃 1과 같은 예외를 쓴다. 실행 전에 사람이 확인한다.
- 사운드 합성 값 (주파수, 길이)은 에이전트 제안이다. 기획서 7장에 `(에이전트 제안)` 표기.
- 승리 가능성 숫자 (85, 91, 80)는 에이전트 계산값이며 저장소에 재현 스크립트가 없다. 기획서에 적지 않는다.

## 9. ADR

- **Decision**: 옵션 A. `LAYOUTS` 배열 + 순차 전이, 판 점수는 누적 촛불 수, 최고 점수는 localStorage 키 1개, 순수 함수 분리.
- **Drivers**: 60초 검증 가능성, 기획서 숫자와 테스트 일치, goal-1~3 동작 보존.
- **Alternatives considered**: 레이아웃별 모듈 파일 (AGENTS.md 충돌), 승리 판만 최고 점수 (D3에서 사용자 기각), 시작 화면에 최고 점수 표시 (추가 기능, 기각).
- **Why chosen**: AGENTS.md 규칙과 충돌이 없고, 전환 규칙이 한 함수에 모이며, 최고 점수 로직이 테스트 가능하다.
- **Consequences**: `levels.js`, `logic.js`, `main.js`, `index.html` 호출부 리팩터링. 기존 테스트 일부 수정.
- **Follow-ups**: 사람 브라우저 확인 (AC-4.x, AC-5.x 전부). AC-4.9 실패 시 기획서 먼저 수정.
