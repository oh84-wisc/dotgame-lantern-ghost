## 1. RALPLAN-DR 요약

**Principles (4)**
1. 기획서가 기준이다. 숫자는 기획서에서 가져오고, 코드가 하는 일을 그대로 적은 테스트를 쓰지 않는다 (AGENTS.md).
2. 턴 판정 순서 (2장 1~9)는 레이아웃 1·2·3에서 똑같이 적용한다. 레이아웃별 예외 규칙을 만들지 않는다.
3. 맵 데이터와 로직을 분리한다. 레이아웃마다 `{ rows, patrol }` 데이터를 두고 logic.js는 상태만 받는다.
4. 새 기능은 기획서에 적힌 것만 만든다. 사운드는 Web Audio 합성음만, 저장은 키 1개.

**Decision Drivers (top 3)**
1. 레이아웃 2·3 맵이 "풀린다"는 것을 사람이 플레이하기 전에 기계로 확인할 수 있어야 한다 (60초 안에 이길 수 있어야 함).
2. 누적 점수와 레이아웃 전환 규칙이 한 곳(logic.js)에서 정의되어야 테스트가 기획서 숫자를 직접 검증할 수 있다.
3. 기존 goal-1~3 동작 (레이아웃 1 AC-1.x ~ AC-3.x)을 깨지 않는다.

**Viable Options**

- **옵션 A (채택): 레이아웃 데이터 배열 + 순차 진행 상태 머신**
  - 장점: `LAYOUTS = [layout1, layout2, layout3]`, `createState`가 `layoutIndex`를 받아 grid와 patrol을 꺼낸다. 전환 규칙이 `logic.js` 한 함수에 모인다.
  - 단점: PATROL_1 이름을 `PATROL` 배열로 바꾸는 리팩터링이 필요하다 (호출부 4곳 안).
- **옵션 B: 레이아웃마다 별도 모듈 파일 (`levels/layout2.js`, `levels/layout3.js`)**
  - 장점: 파일 분리가 명확하다.
  - 단점: AGENTS.md "src/levels.js에 복사" 규칙과 어긋난다. 새 파일 3개를 늘릴 이유가 없다.
- 옵션 B는 AGENTS.md와 충돌하므로 기각. 옵션 A를 채택한다.

## 2. 레이아웃 2·3 (goal-4)

### 2.1 설계 규칙

- 규격 20열 × 15행, 바깥 테두리는 `#`.
- 촛불 수: 레이아웃 2 = 14개, 레이아웃 3 = 16개 (스펙 R2 범위 10~20 충족).
- 경비병 순찰 고리: 레이아웃 2 = 10칸, 레이아웃 3 = 12칸 (스펙 R13 범위 8~12 충족). 고리는 모두 바닥(`.`, `G`)이고 연속한 칸은 상하좌우로 인접한다.
- `G` 칸 = 순찰 고리의 첫 칸 (`index 0`). `S` 칸은 고리에 들어가지 않는다.
- 모든 촛불은 `S`에서 벽을 피해 걸어서 닿을 수 있다 (정적 연결성 검사 통과).
- 승리 가능성: 2장 판정 순서 1~9를 그대로 적용한 완전 탐색 (BFS)으로 최단 턴 수를 구했다.

### 2.2 설계 검증 결과 (에이전트 검증, 기계 탐색)

| 레이아웃 | 촛불 | 순찰 고리 | 최단 승리 턴 | 검증 |
|---|---|---|---|---|
| 1 (기존) | 12 | 8 | 85 | 같은 솔버로 기존 맵이 풀림을 확인 (기준선) |
| 2 (신규) | 14 | 10 | 91 | 승리 가능 |
| 3 (신규) | 16 | 12 | 80 | 승리 가능 |

- 최단 턴 수는 키 한 번당 120 ms 잠금을 고려하면 최소 약 9.6 s ~ 10.9 s 분량이다. 60초 제한 안에 사람이 플레이할 수 있는지는 사람이 브라우저에서 확인한다 (AC-4.4, AC-4.6). 제한 시간 숫자는 바꾸지 않는다.
- 솔버 파일과 맵 텍스트는 기획서 5장 원문과 동일해야 한다. 기획서에 옮긴 뒤 `levels.js`는 기획서 문자열을 그대로 복사한다.

### 2.3 레이아웃 2 (14 촛불, 순찰 10칸)

```
####################
#S..c..c..#..c.c.#.#
#.#######.#......#.#
#.........#.#####..#
#.c#......#........#
#..#.####.....#...##
#..#........c.#.c.##

#.#####.#.#......#.#
#.........#......#.#
#c..#.#####..##..#.#
#...#.....#.G......#
#...#..cc.#......c.#
####################
```

- 유령 시작 `S`: 열 1, 행 2 (열은 0부터, 행은 1부터 센다: 기획서 9장 AC-3.6 표기와 같다)
- 경비병 시작 `G`: 열 12, 행 13
- 순찰 고리 (열, 행, 열은 0부터, 행은 1부터): (12,13) → (13,13) → (14,13) → (15,13) → (15,12) → (15,11) → (14,11) → (13,11) → (12,11) → (12,12) → (12,13) …
  - 코드 값 (열, 행-1): `[[12,12],[13,12],[14,12],[15,12],[15,11],[15,10],[14,10],[13,10],[12,10],[12,11]]`

> 주의: 위 순찰 고리 좌표는 솔버 입력값 기준으로 적었다. 기획서에 옮길 때 행 번호를 한 번 더 확인하고, `G` 칸과 순찰 첫 칸이 같은지 테스트로 확인한다 (test/levels.test.js).

### 2.5 레이아웃 순서와 전환

- 순서 고정: 레이아웃 1 → 2 → 3 (스펙 R14).
- 레이아웃 1·2 승리 시: 누적 촛불 수에 그 레이아웃의 촛불 수를 더하고, 다음 레이아웃을 `S`에서 시작, 타이머 60000 ms, 유령 상태 초기화. 화면은 `playing` 유지.
- 레이아웃 3 승리 시: `screen: "win"` (최종 화면). 누적 42/42.
- 패배 (잡힘, 시간 초과) 시: 누적 촛불 수는 그 순간까지 켜진 수 (이전 레이아웃 합 + 현재 레이아웃 켜진 수).

### 2.6 표시 분모

- 게임 화면 HUD, 패배 화면, 최종 화면 모두 `켜진 촛불 N/42`를 쓴다. 분모 42 = 12 + 14 + 16 (전체 촛불 합). 레이아웃별 분모는 보이지 않는다.

- AC-4.3: 레이아웃 2에서 촛불 14개를 모두 밟으면 레이아웃 3이 바로 나온다 (승리 화면 아님). 타이머는 60초, 촛불 표시는 `켜진 촛불 26/42`.
- AC-4.4: 레이아웃 3 순찰 고리는 12칸 주기다. 기획서 5장 2.4의 최단 승리 (80턴 분량)를 사람이 60초 안에 따라갈 수 있다 (정확한 경로 미리 공개하지 않음).
- AC-4.5: 레이아웃 2·3에서 경비병 시야 칸을 밟거나 경비병 칸으로 들어가면 즉시 패배 화면이 뜨고 `켜진 촛불 N/42`가 있다. N은 그 순간의 누적 수 (레이아웃 2에서 진 판이면 12 + 현재 레이아웃 켜진 수).
- AC-4.6: 레이아웃 3에서 촛불 16개를 모두 밟으면 최종 화면이 뜬다. 최종 화면에 `총 켜진 촛불 42/42`가 있다.
- AC-4.7: 레이아웃 1·2·3 어디서든 [다시 시작]은 레이아웃 1로 돌아가고, 누적 촛불 수가 0이 된다.

**goal-5 (사운드·최고 점수·최종 화면)**
- AC-5.1: [시작] 클릭 후 촛불을 밟으면 짧은 소리가 난다. 파일 요청이 0개다 (개발자도구 Network 탭에서 확인).
- AC-5.2: 레이아웃 1·2 클리어 시 상승음, 패배 시 하강음, 최종 승리 시 3음 상승음이 난다. 소리 끄기 버튼이 없다.
- AC-5.3: 승리 또는 패배 후 개발자도구 Application > Local Storage에 키 `lantern-ghost.highScore` 1개만 있고 값은 숫자 문자열이다.
- AC-5.4: 새로고침 후에도 최고 점수가 그대로 보인다. 더 낮은 점수로 끝난 판은 최고 점수를 낮추지 않는다.
- AC-5.5: 최종 화면에 `총 켜진 촛불 42/42`, `최고 점수 N`, [다시 시작], [처음으로] 4개가 보인다. [처음으로]는 시작 화면, [다시 시작]은 레이아웃 1로 간다.
- AC-5.6: 화면 전체 색은 기획서 6장 8색 hex만 쓴다 (사람이 hex를 `src/sprites.js`와 대조).
- AC-5.7: 외부 이미지·오디오·폰트 파일 요청이 0개다 (웹폰트 1개 예외는 쓰지 않는다).

## 8. 위험과 열린 질문

- 최단 턴 수 80~91턴은 60초 안에서 빠듯할 수 있다. 숫자는 바꾸지 않는다. 사람 플레이에서 안 되면 맵을 고치기 전에 기획서를 먼저 고치고 사람에게 보여준다 (AGENTS.md).
- AGENTS.md "좌표를 따로 적지 않는다"와 순찰 고리 좌표는 기존 레이아웃 1 방식 (PATROL_1)을 그대로 따른다. 이 예외를 계속 쓸지 실행 전에 사람이 확인한다.
- 사운드 합성 값 (주파수, 길이)은 에이전트 제안이다. 기획서 7장에 `(에이전트 제안)` 표기.

## 9. ADR

- **Decision**: 옵션 A 채택. 레이아웃 배열 `LAYOUTS` + 순차 상태 전이, 판 점수는 누적 촛불 수, 최고 점수는 localStorage 키 1개.
- **Drivers**: 60초 검증 가능성, 기획서 숫자와 테스트 일치, goal-1~3 동작 보존.
- **Alternatives considered**: 레이아웃별 모듈 파일 (AGENTS.md 충돌), 승리 판만 최고 점수 (D3에서 사용자 기각).
- **Why chosen**: AGENTS.md 규칙과 충돌이 없고, 전환 규칙이 한 함수에 모인다.
- **Consequences**: `levels.js`와 `logic.js` 호출부 리팩터링. 기존 테스트 수정 필요.
- **Follow-ups**: 사람 브라우저 확인 (AC-4.x, AC-5.x 전부).
