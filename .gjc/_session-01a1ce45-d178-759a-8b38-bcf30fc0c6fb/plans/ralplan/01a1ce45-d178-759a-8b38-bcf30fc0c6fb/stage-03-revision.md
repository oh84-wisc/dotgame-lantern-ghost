이 문서는 계획이다. 코드는 쓰지 않는다. 기획서 반영은 이 계획을 사람이 승인한 뒤에 한다.
기획서 숫자는 바꾸지 않는다. 아래 "제안 값"은 기획서에 없던 값이라 승인 전까지 기획서에 넣지 않는다.

## 좌표 표기 (통일)
- 열은 0부터, 행은 5장 문자 줄 기준 1부터 센다. 예: `S`는 (열1, 행2), `G`는 (열9, 행14).
- 테스트 기대값도 이 표기를 쓴다.

## RALPLAN-DR 요약

### 원칙
1. 기획서 숫자는 바꾸지 않는다. 기획서에 없는 값은 제안으로만 적고, 사람 승인 뒤 기획서 2·5장에 넣는다 (AGENTS.md).
2. 턴제: 유령 한 칸 이동 + 경비병 한 칸 이동 = 한 턴. 실시간은 60초 시계뿐이다.
3. 로직은 canvas를 모르는 순수 함수 (src/logic.js). 시간 경과는 인자로 받는다.
4. 수용 기준은 브라우저에서 사람이 눈으로 yes/no 답할 수 있어야 한다.

### 결정 동인
1. 2장 확정 숫자 (16px, 320x240, 120ms, 60초, 시야 앞 1칸, 순찰 8~12칸)와 충돌하지 않을 것.
2. HUD는 캔버스 밖에 둔다. 320x240과 5장 레이아웃은 그대로.
3. 판정 순서와 순찰 경로가 기획서에 있어야 AC와 단위 테스트 기대값을 쓸 수 있다.

### 선택지
- A. 턴제 경비병 (확정): 유령 한 칸 = 경비병 한 칸.
- B. 실시간 경비병: 기각. 2장 턴제 규칙과 충돌.

## 확정 결정 (사용자 응답, intent)
- HUD: 캔버스 밖 HTML 텍스트 (타이머, 켜진 촛불 수 N/12).
- 화면 흐름: 시작 화면 포함. 승리·패배 화면에 "다시 시작" + "처음으로".
- 시간 초과 점수: 그때 켜진 촛불 수. 기획서 2장에 점수 규칙 추가.
- 경비병: 유령 한 칸 = 경비병 한 칸.
- 경비병 시야: 순찰 경로의 진행 방향을 따른다.

## 제안 값 (기획서에 없음, 사람 승인 필요)

### P1. 순찰 경로 (5장에 추가할 값)
- 시작: G (열9, 행14). 시작 시 시야 방향은 경로상 다음 칸 (열10, 행14) 방향 = 동쪽.
- 8칸 고리, 반복 (왕복 아님):
  (9,14) → (10,14) → (11,14) → (12,14) → (12,13) → (11,13) → (10,13) → (9,13) → (9,14) …
- 고리 길이 8. 2장 "8~12칸" 범위 안.
- 모든 칸은 5장에서 `.`이다 (벽·촛불 없음). 검사: 행14 열9~12 `.`, 행13 열9~12 `.`.
- 경비병 상태: pathIndex (0~7), 시야 방향 = 현재 칸에서 다음 칸으로 가는 방향.
- 시야 칸 = 경비병 칸 + 시야 방향으로 1칸. 그 칸이 벽이면 칠하지 않고 패배 판정도 없다.
- 이 고리에서 시야가 바뀌는 칸은 4개 모서리이므로 AC-2.4(방향 전환)를 사람이 볼 수 있다.

### P2. 한 턴의 판정 순서 (2장 나머지에 추가할 값)
입력은 유령 이동 한 번에 대응한다. 순서는 아래 번호대로 고정한다.
1. 목표 칸이 벽이거나 범위 밖이면: 아무 것도 바뀌지 않는다. 경비병도 움직이지 않는다. 턴 소모 없음.
2. 유령이 목표 칸 T로 이동한다.
3. T가 꺼진 촛불이면 켠다. 촛불은 되돌아가지 않는다.
4. T가 경비병의 현재 칸이면: 패배 (유령이 경비병에게 간다). 여기서 끝.
5. 경비병이 고리에서 한 칸 이동하고 시야 방향을 갱신한다.
6. 경비병의 새 칸이 유령 칸 T와 같으면: 패배 (경비병이 유령에게 온다).
7. 경비병의 새 칸이 유령의 이전 칸이고 유령 칸 T가 경비병의 이전 칸이면 (서로 맞바꿈): 패배.
8. 유령 칸 T가 경비병의 새 시야 칸과 같으면: 패배 (시야 판정은 경비병이 움직인 뒤의 시야로 한다).
9. 촛불 12개가 모두 켜졌으면: 승리. 패배 판정(4, 6, 7, 8)이 먼저다. 같은 턴에 패배와 마지막 촛불이 겹치면 패배.
10. 턴 처리 후 타이머가 0 이하이고 승·패가 없으면: 패배 (시간 초과).

- 시간 초과와 입력이 겹치는 경우: 입력은 타이머가 0이 되기 전 처리된 것만 유효하다. 타이머가 0이 되면 입력을 받지 않는다. 이미 끝난 게임은 입력을 무시한다.
- 120 ms 이동 중 들어온 방향키는 무시한다 (큐에 쌓지 않는다). 시작·승패 화면에서는 방향키를 무시하고 버튼 클릭만 받는다.
- 방향키 기본 동작은 막는다 (2장 확정).

### P3. 상태 계약 (계획 내부, 기획서에는 쓰지 않음)
- state = { grid, ghost:{x,y}, lit: 촛불 좌표 집합, guard:{pathIndex, x, y, facing}, timeLeft, screen }
- logic.js 함수: `stepTurn(state, direction)` → 새 state (판정 순서 P2 적용). `tick(state, elapsedMs)` → 새 state (타이머 감소, 0 이하면 패배).
- 타이머 감소, 120 ms 입력 잠금, setInterval/rAF는 main 쪽. logic.js에 시계 호출 없음.
- 화면 전환(시작·게임·승리·패배)도 screen 값으로 표현하고 main이 그린다.

### P4. 레이아웃 1 승리의 범위
- 2장 "레이아웃 3개를 고정된 순서로 진행"은 유지한다. R2에서는 레이아웃 1 승리를 최종 승리로 쓴다. 이 한정 문구를 2장 해당 행에 "R2: 레이아웃 1만 구현, 승리 = 최종 승리"로 추가한다.
