# Architect 검토 (R2 revision stage-02, pass 1)

## Summary
계획은 턴제·HUD 캔버스 밖·순수 logic.js 원칙을 지키고 2장 확정 숫자(16px, 320x240, 120ms, 60초, 시야 1칸, 순찰 8~12칸)를 바꾸지 않는다. 구조 경계 위반은 없다. 다만 순찰 경로의 정의 위치, 판정 순서, 레이아웃 1 승리=최종 승리 선언이 기획서에서 먼저 확정되어야 한다. 차단 사유는 아니므로 WATCH.

## Claims
1. 구조 경계: 위반 없음. logic.js 순수 유지, hex는 sprites.js 한 곳, 맵은 levels.js 문자 복사. 단, 계획이 상태 계약(timeLeft, lit 촛불, 경비병 순찰 인덱스/방향, 화면 상태)을 명시하지 않았다.
2. 2장 확정값 충돌: 직접 충돌 없음. 간접 충돌 1건: '레이아웃 1 승리가 최종 승리' 는 2장 '레이아웃 3개를 고정 순서로 진행'(스펙 R7,R14)을 R2 한정으로 재해석한다. 5장은 레이아웃 2,3을 R2 이후로 미뤘으므로 모순은 아니지만 기획서 3장/2장에 'R2 한정' 문구로 명시해야 한다.
3. 기획서에 없는 기능: 시작 화면, '다시 시작', '처음으로', 점수 N/12는 계획 문서가 사용자 응답으로 확정했다고 기재한 항목이므로 허용. 단 7장(UI 텍스트)은 R3 소관이고 AGENTS.md는 UI 문구를 src/strings.js 한 곳에 두라고 한다. 계획에 문구 위치가 없다. 추가로 HTML HUD/화면의 글자색·배경색이 8색 밖 hex를 도입할 위험이 있다 (현재 index.html에는 hex 없음).
4. 미확인 기본값 중 위험 최대: 판정 순서.

## Analysis
### 판정 순서 (위험 큼)
'유령 먼저 이동, 도착 칸에서 시야 판정'만으로는 불충분하다. 경비병은 유령 이동 뒤에 움직이는데, (a) 이동 전 시야로 판정하는지, 경비병 이동 후 새 시야로 재판정하는지, (b) 경비병이 시야를 돌리거나 이동해 유령 칸을 덮는 경우 패배인지, (c) 유령이 경비병 본체 칸에 들어가는 경우(시야 정의가 앞 1칸뿐이라 본체 칸은 시야가 아니다), (d) 유령과 경비병이 서로 자리를 맞바꾸는 경우, (e) 벽에 막혀 이동 실패한 입력이 턴을 소모하는지(AC-2.3 '한 칸 움직일 때마다')가 정해지지 않았다. 2장 '시야 안에 들어가는 순간 즉시 패배' 는 유령 행동 기준으로 읽히지만 경비병 이동 후 재판정은 해석이 갈린다. AC-3.1과 단위 테스트의 기대값이 이 순서에 직접 의존하므로 기획서 2장 나머지에 표로 못박아야 한다. 같은 칸/인접 칸 문구는 의미가 모호하여 삭제하고 위 (a)-(e)로 대체할 것.
### 순찰 경로 (계획 누락)
2장은 고정 경로 8~12칸이라 했으나 계획과 5장 어디에도 경로가 없다. AGENTS.md는 맵 좌표를 따로 적지 않고 문자만 levels.js에 복사하라고 한다. 경로 데이터의 위치(기획서 5장에 방향 문자열 등으로 추가 후 levels.js 복사)와 왕복/순환 여부가 정해져야 AC-2.3, AC-2.4 검증이 가능하다. 경로 길이(8~12) 선택은 2장 범위 안에서 기획서에 숫자로 확정해야 한다. 코드에서 정하면 '기획서 숫자를 코드에서 바꾸지 않는다' 위반.
### 벽이 시야를 막음 (위험 낮음)
시야가 앞 1칸이라 사실상 '벽 칸은 칠하지 않는다'뿐이다. 2장 시야 정의와 충돌 없음. 패배 판정과 칠하기가 같은 함수를 쓰도록만 하면 된다. 뒤집혀도 영향이 작다.
### AC 번호 AC-x.y (위험 낮음)
기획서 9장의 번호 체계 요구(아직 안 정한 것 7)를 채울 뿐이며 코드에 영향이 없다. 단 goal-3 AC에 타이머 0에서 정지, 승리·패배 시 타이머 정지/입력 차단 항목이 없다.
### 기타 누락
- 타이머: 시작 화면에서 [시작] 시점에 시작, 재시작 시 60으로 리셋, 종료 화면에서 정지 — 계획에 없음. logic은 경과 시간을 인자로 받는 순수 함수여야 하고 setInterval/rAF는 main 쪽에 있어야 한다.
- 시간 초과와 같은 틱에서 승리가 겹치는 순서 미정(승리 우선인지).
- 승리 시 점수/화면 문구 없음(필수 아님).
- 좌표 표기: 기획서 'G 9열 14행'은 열 0-기준, 행 1-기준처럼 읽히는 혼용이다. 계획이 그대로 복사했으므로 테스트 기대값 작성 시 혼동 주의.
- 2장 '시간 초과 점수' 규칙 추가는 기획서 '아직 안 정한 것 2'의 해소로서 정당하다. 단 4장 4·5색 사용 시점(안 정한 것 8)과 시야 방향 4, 경비병 동기 3, 벽 6, AC 7번을 기획서에서 함께 닫아야 한다.

## Root Cause
판정/순서 규칙과 순찰 경로 데이터가 기획서에서 정해지지 않은 채 계획이 AC를 먼저 쓰고 있다. AGENTS.md 상 기획서가 유일한 기준이므로 구현 전에 기획서 2장·5장에서 닫아야 한다.

## Findings
- MEDIUM: 판정 순서 (a)-(e) 미정. 계획 '미확인 기본값 2'. 임의 구현 시 AC-3.1 재현 불가. 수정: 2장 나머지에 턴 순서 표 추가.
- MEDIUM: 순찰 경로 정의 위치/형태/길이 누락. 수정: 5장에 경로 규칙 추가, levels.js에는 복사만.
- LOW: '레이아웃 1 승리 = 최종' 문구가 2장 '3개 순서 진행'과 충돌하지 않도록 R2 한정으로 명시.
- LOW: UI 문구는 src/strings.js, HTML HUD 색은 8색 hex만 쓰고 hex는 sprites.js 한 곳 원칙과 충돌하지 않게 처리 방안 필요 (CSS는 JS로 주입하거나 중립 처리).
- LOW: 타이머 시작/정지/리셋과 승리-시간초과 동시 틱 규칙 누락.

## Recommendations
1. 기획서에 판정 순서를 표로 확정: 입력 → 벽이면 무효(턴 소모 안 함) → 유령 이동 → 촛불 점화 → 경비병 한 칸 이동 및 시야 갱신 → 패배 판정(최종 시야 칸 = 유령 칸) → 승리 판정. 이 순서가 안 맞으면 사람이 뒤집을 것. 최소 (a)-(e)를 계획에 포함.
2. 순찰 경로를 기획서 5장에 확정하고 levels.js는 복사.
3. 상태 계약을 계획에 한 줄로: { grid, ghost, lit, guard:{pathIndex,dir}, timeLeft, screen } 순수 함수 + 경과 시간 인자.
4. 레이아웃 1 승리 = R2 한정 최종 승리 문구 추가.
