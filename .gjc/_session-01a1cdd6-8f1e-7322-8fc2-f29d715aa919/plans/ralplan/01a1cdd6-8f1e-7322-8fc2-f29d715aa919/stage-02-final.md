## 1. Principles

1. **기획서가 먼저, 코드는 그 다음.** R1 코드는 GAME_DESIGN.md 4·5·6장(및 9장 R1 해당분)이 사람 승인으로 확정된 뒤에만 시작한다 (AGENTS.md: "기획서가 애매하면 기획서를 먼저 고치고 사람에게 보여준 뒤 코드를 쓴다").
2. **R1 범위는 이동 하나.** 촛불 점화, 경비병 순찰·시야·패배, 60초 시계, 점수, 레이아웃 전환, 화면 흐름은 R1에 넣지 않는다. 맵 데이터에 해당 문자가 있어도 R1 로직은 이동과 그리기만 다룬다.
3. **(에이전트 제안) 값은 승인 전까지 확정값이 아니다.** 2장의 한 칸 이동 시간·타일 크기·화면 크기, 그리고 0단계 초안의 모든 값은 사람이 승인하고 표기를 제거하기 전까지 코드 상수·테스트 기대값으로 쓰지 않는다.
4. **순수 로직 / 화면 분리, 단방향 의존.** `src/logic.js` 는 canvas·DOM·키 이벤트를 모르는 순수 함수(상태 → 새 상태)만 둔다. 의존은 데이터(levels.js) 쪽으로만 흐른다.
5. **의존성 0, 빌드 0, 데이터는 복사.** package.json·npm·번들러·이미지 파일 없이, 맵은 5장 문자 격자를 levels.js에 그대로, 색은 6장 8색 hex만, 스프라이트는 팔레트 인덱스 배열로.

## 2. Decision Drivers (상위 3개)

1. **기획서 공백이 구현을 막는다.** 4장(범례·이동 차단 규칙), 5장(맵), 6장(팔레트), 유령 시작 타일, 2장 (에이전트 제안) 값이 비어 있거나 미확정이다. 이 값 없이는 levels.js·sprites.js·canvas 크기·테스트 기대값을 만들 수 없다.
2. **AGENTS.md 코드 규칙 준수.** logic.js 순수성, 5장 그대로 복사, 6장 8색만, UI 문구는 strings.js 한 곳, 기획서 숫자 기반 테스트, 금지 기능 목록.
3. **완료 판정 가능성.** 완료 = 9장 수용 기준 + 사람의 브라우저 확인. 9장이 비어 있으면 R1 goal은 구조적으로 닫히지 않는다. 9장 처리 방식을 계획에서 결정해야 한다.

## 3. Viable Options

### 3.1 코드 구조

**옵션 A — logic.js(순수) + index.html 인라인 module 스크립트가 입력·그리기 담당 (채택)**
- 장점: AGENTS.md가 열거한 파일(src/logic.js, levels.js, sprites.js, strings.js, index.html)만 쓴다. 새 파일·새 규칙 없음.
- 단점: 키→방향 매핑이 index.html 인라인에 있어 자동 테스트 불가. R1 규모에서 수용하고 사람 브라우저 확인으로 덮는다.

**옵션 B — 입력·그리기를 별도 모듈(src/main.js 등)로 분리**
- 장점: index.html이 얇아지고 화면 코드 경계가 분명하다.
- 단점: AGENTS.md 코드 규칙에 없는 파일 추가. R1(이동 하나)에서 이득이 작다. 사람이 파일 구조를 승인할 때만 채택.

**옵션 C — 키 입력 시 120 ms 동안 칸 사이를 보간하는 애니메이션 (배제)**
- 장점: 움직임이 부드럽다.
- 단점: 120 ms는 (에이전트 제안) 값이라 Principle 3에 걸린다. 배제: 키 입력 즉시 다음 칸에 다시 그린다. 이동 시간이 승인되면 그 값으로 재계획한다.

### 3.2 9장(수용 기준) 처리

**옵션 9-a — R1 해당 수용 기준을 9장에 선행 작성 (권고)**
- 0단계에서 에이전트가 9장에 수용 기준 번호 체계(미정 10번)와 R1 해당 항목만 "(에이전트 제안)"으로 초안 작성 → 사람 승인. 9장의 나머지(R2 이후 항목)는 "R2에서 채운다" 그대로 둔다.
- 장점: R1 goal에 완료 경로가 생긴다. 새 기능이 아니라 문서 작성 순서 변경이다. §5·§7의 번호 자리를 R1 안에서 채울 수 있다.
- 단점: GAME_DESIGN.md의 "9장: R2에서 채운다" 표기를 사람 승인으로 바꿔야 한다. R2에서 번호 체계를 바꾸면 R1 항목 번호를 다시 맞춰야 한다 (번호 체계를 0단계에서 확정하는 이유).

**옵션 9-b — 9장은 R2까지 대기**
- 장점: 기획서의 라운드 계획을 그대로 지킨다.
- 단점: R1은 "구현·테스트 완료, 수용 기준 매핑 대기"로만 보고된다. AGENTS.md 완료 조건상 R1 goal을 닫을 수 없고, goal 하나 = 커밋 하나 규칙과 겹쳐 R1 커밋 시점이 애매해진다.

**권고: 옵션 9-a.** 사람이 9-b를 고르면 §5·§7은 "번호 대기" 상태로 실행하고 R1 보고 문구를 "구현됨, 수용 기준 미매핑"으로 한정한다.

**승인 대상 — 2장 (에이전트 제안) 값 3개**
- 한 칸 이동 시간 (현재 "120 ms (에이전트 제안)"). R1은 애니메이션이 없으므로(옵션 C 배제) 값 자체는 R1 코드에 쓰이지 않지만, 확정 여부는 사람이 정한다.
- 타일 크기 (현재 "16 × 16 px (에이전트 제안)") — sprites.js 스프라이트 변 길이, canvas 크기의 전제.
- 화면 크기 (현재 "320 × 240 px = 20 × 15 타일 (에이전트 제안)") — canvas 크기, 5장 격자 행·열 수의 전제.

**4장 오브젝트 — 필수 확정 항목 (보류 불가)**
- 4-1. 맵 문자 범례: 5장 격자에 쓰는 모든 문자와 의미 (최소: 바닥, 벽, 유령 시작, 촛불, 경비병 시작). 문자당 한 의미.
- 4-2. 이동 차단 규칙: 유령이 벽 칸으로 이동하려 할 때, 맵 가장자리 밖으로 이동하려 할 때의 결과.
- 4-3. 통행 가능 칸: 유령 시작 문자 칸, 촛불 문자 칸, 경비병 시작 문자 칸을 R1 이동에서 바닥(통행 가능)으로 취급하는지. (촛불은 2장 "촛불 타일에 들어서면"에서 진입 가능이 도출되나 문서로 명시. 경비병 시작 칸은 기획서 근거 없음 → 반드시 결정.)
- 4-4. 차단 이동의 반환 계약: 차단 시 `moveGhost` 가 위치가 같은 새 상태 객체를 돌려주는지, 입력과 동일한 상태 객체를 돌려주는지. 어느 쪽이든 유령 위치는 변하지 않는다.
- 4-5. 잘못된 direction 처리: 네 방향 외 값이 들어올 때의 결과 (예외 / 상태 불변 반환 중 하나).
- 4-6. R1 화면 표시 규칙: 유령이 떠난 뒤 시작 칸의 모양(바닥으로 그림), 촛불 칸의 R1 정적 표시 여부, **경비병 시작 칸 표시 방식(경비병 스프라이트 vs 바닥)**.

**5장 레벨 맵 — 필수 확정 항목**

### 0.5단계 — 실행 환경 스모크 (코드 착수 직전)
- `node --version` 출력 기록.
- `test/smoke.test.js` 대신 R1 실제 테스트 파일 하나를 최소 형태로 먼저 만들고 `node --test test/` 를 실행해, (a) 디렉터리 인자로 테스트 파일이 발견되는지, (b) package.json 없이 `src/*.js` ES 모듈 import가 되는지 확인한다. 별도 스모크 전용 파일은 남기지 않는다.
- 실패 시 보고 기준: package.json 추가·플래그 우회·파일 확장자 변경(.mjs) 같은 우회를 **임의로 하지 않고** 멈춘다. 보고 내용 = Node 버전, 실행 명령, 오류 원문 첫 줄, 실패 유형(테스트 미발견 / ESM import 실패 / 기타). 해결 방식(예: .mjs 사용, 명령 변경)은 AGENTS.md 명령어·코드 규칙 변경이므로 사람이 결정한다.

### 의존 방향 (고정)
- `src/levels.js` = 데이터 + 범례 문자 상수의 단일 출처. 다른 src 모듈을 import하지 않는다.
- `src/logic.js` → levels.js (범례만). canvas·DOM·sprites.js import 금지.
- `src/sprites.js` → levels.js (범례). **6장 팔레트 hex 배열의 단일 출처는 sprites.js.** logic.js를 import하지 않는다.
- `index.html` → logic.js, levels.js, sprites.js, (필요 시) strings.js.
- 금지: logic.js → sprites.js, levels.js → 그 외 모듈, 팔레트 hex를 sprites.js 밖에 다시 적기.

### src/levels.js — 근거: 5장(맵), 4장(범례), 2장(레이아웃 순서 3개 고정)
- 5장 레이아웃 3개 문자 격자를 문자열 배열로 **그대로 복사**. 좌표 목록을 따로 적지 않는다.
- 5장 고정 순서대로 배열에 넣는다. R1 화면은 순서상 첫 레이아웃만 사용. 레이아웃 전환은 R1 범위 밖.
- 4장 범례 문자를 영문 이름 상수로 export.

### src/logic.js — 근거: 2장 "조작: 방향키 한 번 = 유령이 한 칸 이동"(스펙 R11), 4장 4-2~4-5, 5장
- **상태 형태:** `{ grid, ghost: { x, y } }`. `grid` 는 5장 격자(불변, 이동으로 바뀌지 않음), `ghost` 는 위치만. 유령 위치를 격자 문자로 표현하지 않는다.
- `createState(levelRows)`: 격자에서 유령 시작 문자 위치를 찾아 `ghost` 를 만든다. `grid` 는 원본 그대로 보관 (시작 문자 칸의 통행·표시는 4-3·4-6 규칙으로 해석).
- `moveGhost(state, direction)`: direction ∈ {up, down, left, right}. 정확히 한 칸. 목적지가 4-2·4-3 규칙상 통행 가능하면 새 위치의 새 상태를, 차단이면 4-4 계약대로 반환. 잘못된 direction은 4-5대로. 입력 상태를 변경하지 않는다.
- 통행 판정 헬퍼(예: `isWalkable(grid, x, y)`)는 4장 범례·규칙만 사용.
- 촛불 점화, 경비병, 시야, 패배, 시계, 점수 함수는 만들지 않는다.
