# R1 구현 계획 — Planner 산출물 1 (Lantern Ghost)

기준 문서: 저장소 루트 `GAME_DESIGN.md` (v0), `AGENTS.md`. 근거 스펙: `.gjc/_session-01a1cdd6-.../specs/deep-interview-dotgame-ghost-candles.md`.

R1 goal (단 하나): **맵 위에서 캐릭터(유령)가 한 칸씩 움직인다.**

저장소 현황(조사 결과): `src/`, `test/`, `index.html` 은 아직 없다. 존재하는 파일은 `GAME_DESIGN.md`, `AGENTS.md`, `.gjc/` 뿐이다. GAME_DESIGN.md 4장(오브젝트)·5장(레벨 맵)·6장(팔레트)은 "R1에서 채운다"로 비어 있고, 9장(수용 기준)은 "R2에서 채운다"로 비어 있다.

표기: 이 계획에서 **미정** 은 기획서에 값이 없어 사람이 정해야 하는 항목이다. 계획은 미정 항목에 값을 채우지 않는다.

---

## 1. Principles

1. **기획서가 먼저, 코드는 그 다음.** R1 코드 작업은 GAME_DESIGN.md 4·5·6장이 사람 확인을 거쳐 채워진 뒤에 시작한다 (AGENTS.md: "기획서가 애매하면 기획서를 먼저 고치고 사람에게 보여준 뒤 코드를 쓴다").
2. **R1 범위는 이동 하나.** 촛불 점화, 경비병, 시야·패배 판정, 60초 시계, 점수, 레이아웃 전환, 화면 흐름은 R1에 넣지 않는다. 데이터(5장 맵)에 해당 문자가 있어도 R1 로직은 이동과 그리기만 다룬다.
3. **(에이전트 제안) 숫자는 확정값이 아니다.** 2장의 한 칸 이동 시간·타일 크기·화면 크기는 사람이 확정하기 전까지 코드 상수나 테스트 기대값으로 쓰지 않는다.
4. **순수 로직 / 화면 분리.** `src/logic.js` 는 canvas·DOM·키 이벤트를 모르는 순수 함수(상태 → 새 상태)만 가진다. 입력·그리기는 `index.html` 쪽에서만 한다.
5. **의존성 0, 빌드 0, 데이터는 복사.** package.json·npm·번들러·이미지 파일 없이, 맵은 5장 문자 그리드를 `src/levels.js` 에 그대로, 색은 6장 8색 hex만, 스프라이트는 팔레트 인덱스 배열로.

## 2. Decision Drivers (상위 3개)

1. **기획서 공백이 구현을 막는다.** 5장 맵 문자, 4장 오브젝트(맵 문자 범례 포함), 6장 팔레트, 유령 시작 타일, 타일/화면 크기가 비어 있거나 미확정이다. 이 값 없이는 levels.js·sprites.js·canvas 크기·테스트 기대값을 만들 수 없다.
2. **AGENTS.md 코드 규칙 준수.** logic.js 순수성, 5장 그대로 복사, 6장 8색, strings.js 단일 위치, 기획서 숫자 기반 테스트, 금지 기능 목록.
3. **완료 판정 가능성.** 완료 조건은 9장 수용 기준 + 사람의 브라우저 확인이다. 9장이 R2 예정으로 비어 있으므로, R1은 테스트 통과만으로 "완료"를 선언할 수 없다.

## 3. Viable Options

### 옵션 A — logic.js(순수) + index.html 인라인 모듈 스크립트가 입력·그리기 담당 (권장)
- 장점: AGENTS.md가 열거한 파일(src/logic.js, levels.js, sprites.js, strings.js, index.html)만으로 끝난다. 새 파일·새 규칙이 없다.
- 단점: index.html 스크립트가 R2·R3에서 커지면 분리가 필요해질 수 있다.

### 옵션 B — 입력·그리기를 별도 모듈(예: src/main.js 또는 src/render.js)로 분리
- 장점: index.html 이 얇아지고 화면 코드 경계가 더 분명하다.
- 단점: AGENTS.md 코드 규칙에 없는 파일을 추가한다. R1(이동 하나) 규모에서는 이득이 작다. 추가하려면 사람이 파일 구조를 승인해야 한다.

### 옵션 C — 키 입력 시 120 ms 동안 칸 사이를 보간하며 이동 (애니메이션)
- 장점: 움직임이 부드럽다.
- 단점: 120 ms 는 (에이전트 제안) 값이다. 확정 전 사용 금지 원칙(Principle 3)에 걸린다. **배제**: 사람이 2장 "한 칸 이동 시간"을 확정하기 전까지는 키 입력 즉시 다음 칸에 다시 그린다. 확정되면 그 값으로 재계획한다.

### 결론
옵션 A를 기본으로 한다. 옵션 B는 사람이 파일 구조를 승인할 때만 채택한다. 옵션 C는 위 근거로 배제한다(이동 시간 확정 후 재검토).

그리기 방식: R1에는 시계·경비병이 없으므로 키 입력 시점에만 다시 그린다. requestAnimationFrame 상시 루프는 실시간 시계가 들어오는 라운드(2장 시계, 2장 나머지는 R2)에서 다룬다.

## 4. R1 Plan — 파일별 작업 목록

### 0단계 (코드 이전, 사람 확인 필수): GAME_DESIGN.md 4·5·6장 채우기 — "R1에서 채울 항목"
이 계획은 값을 짓지 않는다. 아래는 채워야 할 **항목 목록**일 뿐이다.
- **4장 오브젝트** (R1에서 채울 항목): 맵에 등장하는 오브젝트 목록과 각 오브젝트의 5장 맵 문자(범례). 최소한 R1 이동에 필요한 것: 유령, 바닥, 벽(이동 차단 여부 포함), 맵 가장자리 처리. 촛불·경비병의 문자 표기도 5장 맵을 쓰려면 함께 정해야 한다. 값: 미정.
- **5장 레벨 맵** (R1에서 채울 항목): 레이아웃 3개의 문자 그리드 (벽, 촛불 10~20개, 유령 시작 타일, 경비병 시작 타일). 그리드 행·열 수는 화면 크기·타일 크기 확정값에 따른다. 값: 미정 (스펙 R10 사용자 보류).
- **6장 팔레트** (R1에서 채울 항목): 8색 hex 값과 각 색의 인덱스 번호. 값: 미정.
- 채운 뒤 사람에게 보여주고 확인받는다. 확인 전에는 아래 코드 단계로 넘어가지 않는다.

### src/levels.js — 근거: 5장 (맵), 4장 (문자 범례), 2장 레이아웃 순서·촛불 개수
- 5장의 레이아웃 3개 문자 그리드를 문자열 배열로 **그대로 복사**한다. 좌표 목록을 따로 적지 않는다.
- 3개를 5장에 적힌 고정 순서대로 배열에 넣는다 (2장 "레이아웃 순서"). R1 화면은 순서상 첫 레이아웃만 사용한다. 레이아웃 전환은 R1 범위 밖.
- 4장 범례 문자를 상수로 둔다 (변수명 영문).

### src/logic.js — 근거: 2장 이동 규칙 "조작" (스펙 R11), 4장 오브젝트, 5장 맵
- canvas·DOM을 import하지 않는다. 모든 함수는 입력 상태를 바꾸지 않고 새 상태를 돌려준다.
- `createState(levelRows)`: 5장 문자 그리드를 읽어 상태 객체 (그리드, 유령 위치) 생성. 유령 위치는 5장의 시작 타일 문자에서 읽는다 (시작 타일: 미정, Open item 3).
- `moveGhost(state, direction)`: 방향 하나 = 정확히 한 칸 (2장 "방향키 한 번 = 유령이 한 칸 이동"). 방향은 up/down/left/right 네 가지.
- 벽 칸으로의 이동, 맵 가장자리 밖으로의 이동: 처리 규칙 **미정** (기획서에 없음, Open item A). 4장에서 확정된 규칙만 구현한다.
- 촛불 점화, 경비병, 시야, 패배, 시계, 점수 함수는 만들지 않는다 (R1 범위 밖).

### src/sprites.js — 근거: 4장 오브젝트, 6장 팔레트, 2장 타일 크기
- R1에서 그리는 오브젝트(4장 확정분: 유령, 바닥, 벽, 그리고 5장 맵에 존재하는 문자 타일)의 스프라이트를 **6장 팔레트 인덱스 배열**로 적는다. 이미지 파일 금지.
- 6장 8색 hex 배열을 이 파일(또는 6장을 그대로 복사한 상수)에서 export 한다. 8색 외 색 금지.
- 스프라이트 한 변의 픽셀 수 = 타일 크기. 타일 크기는 (에이전트 제안) 16×16 상태이므로 **사람이 확정한 뒤** 그 값으로 그린다.
- 촛불·경비병 스프라이트는 5장 맵에 해당 문자가 있어 정적 타일로 보여야 하는 경우에만 4장 정의대로 그린다. 상태 변화(점화, 순찰)는 R1 범위 밖.

### src/strings.js — 근거: AGENTS.md "UI 문구는 src/strings.js 한 군데", 7장 (R3)
- R1 goal은 화면 문구를 요구하지 않고, 7장 UI 텍스트는 R3에서 채운다. **R1에서 화면에 문구를 출력하지 않는다.**
- 문서 제목(`<title>`) 등 R1에서 문구가 필요해지면 그 문구는 기획서에 먼저 적고 strings.js 에만 둔다. 현재 기획서에 해당 문구 없음 → 미정. 기획서 문구가 없으면 R1에서 이 파일을 만들지 않는다 (빈 자리표시 파일 금지).

### index.html — 근거: 2장 조작·화면 크기, 8장 기술 스펙(R3, 비어 있음), AGENTS.md 코드 규칙·명령어
- `<canvas>` 1개 + `<script type="module">`. 외부 스크립트·폰트·이미지 없음 (도트 웹폰트 예외는 R1에서 쓰지 않음).
- canvas 크기 = 화면 크기 확정값 (현재 320×240 은 (에이전트 제안), 확정 전 사용 금지). 반응형·터치 처리 없음.
- 키 입력: 2장 "방향키" 네 개만 `moveGhost` 방향으로 변환. 다른 키 배치는 미정 (Open item 3).
- 키 입력 → `moveGhost` → 결과 상태로 levels/sprites 기반 다시 그리기. 이동 애니메이션 없음 (옵션 C 배제).
- 실행: `python3 -m http.server 8000` 후 `http://localhost:8000/` (ES 모듈은 `file://` 에서 브라우저가 막을 수 있음 — AGENTS.md 명령어 절이 이 대안을 허용).

### test/ — 근거: AGENTS.md "테스트 기대값은 기획서 숫자에서", 2장, 5장
- `test/logic.test.js` (node:test + node:assert, 의존성 없음):
  - 방향 1회 입력 → 유령 위치가 해당 방향으로 정확히 1칸 변함 (2장 "한 칸", 스펙 R11). 네 방향 모두.
  - `moveGhost` 가 입력 상태 객체를 변경하지 않음 (AGENTS.md 순수 함수 규칙).
  - `createState` 의 유령 시작 위치 = 5장 맵의 시작 타일 문자 위치 (5장 확정 후 기대값 작성).
  - 벽·가장자리 이동 결과 = 4장에서 확정된 규칙 (확정 전에는 테스트를 쓰지 않는다).
- `test/levels.test.js`:
  - 레이아웃 개수 = 3 (2장 "레이아웃 순서: 3개", 스펙 R14).
  - 각 레이아웃 촛불 문자 개수가 10~20 범위 (스펙 R2) — 4장 촛불 문자 확정 후.
  - 각 레이아웃 유령 시작 타일 문자가 정확히 1개 — 4·5장 확정 후.
  - 모든 행 길이가 같고, 행·열 수 = 확정된 화면/타일 크기에서 나온 값 (확정 전 기대값 작성 금지).
- 금지: 코드 출력을 그대로 기대값으로 베끼는 테스트, (에이전트 제안) 숫자를 기대값으로 쓰는 테스트.
- 위험 메모: package.json 금지이므로 `src/*.js` ES 모듈을 `node --test` 가 ESM으로 읽으려면 Node의 모듈 문법 자동 감지가 필요하다 (최근 Node는 기본 활성). 실행 Node 버전에서 import 오류가 나면 package.json 추가가 아니라 사람에게 보고한다.

### 순서와 의존성
1. (사람) 2장 (에이전트 제안) 값 확정 여부 결정 + 4·5·6장 채움 + 확인 → 2~5의 전제.
2. src/levels.js (5장·4장 의존)
3. src/logic.js + test/logic.test.js, test/levels.test.js (2~4장 의존)
4. src/sprites.js (4·6장, 타일 크기 의존)
5. index.html (화면 크기, 방향키) → 브라우저 확인
6. 커밋 1개: `goal-1:` 접두사 (AGENTS.md 커밋 규칙). 4·5·6장 기획서 변경은 사람 확인 후 별도 `design-v1:` 커밋이 자연스러우나 커밋 단위는 사람이 정한다.

## 5. Acceptance mapping

- R1 goal "맵 위에서 캐릭터가 한 칸씩 움직인다"가 충족할 9장 수용 기준 번호: **9장 채운 뒤 매핑.**
- 9장은 현재 비어 있고 "R2에서 채운다"로 표기되어 있다. 수용 기준 번호 체계도 미정이다 (아직 안 정한 것 10번).
- 따라서 R1은 9장이 채워지기 전까지 **완료 판정을 할 수 없다.** `node --test test/` 통과는 완료가 아니다 (AGENTS.md 완료 조건). R1 구현이 끝나도 상태는 "구현됨, 수용 기준 미매핑"으로 보고한다.
- 9장이 채워지면 매핑 후보(번호 아님, 내용 기준): ① 방향키 1회 = 1칸 이동, ② 5장 레이아웃 1이 6장 색으로 화면에 보임, ③ 유령이 5장 시작 타일에서 시작, ④ 벽/가장자리 규칙(4장 확정분). 실제 번호는 9장 확정 후 기입.

## 6. Open items (R1 구현 전 사람이 정할 것)

'아직 안 정한 것' 1~11 중 R1에 필요한 항목:
- **1번 — 5장 레벨 맵 내용** (레이아웃 3개의 벽·촛불 배치). R1 levels.js 와 화면의 전제.
- **2번 — 레이아웃별 촛불 개수** (10~20 범위만 있음). 5장 맵을 채우려면 필요. R1 로직은 촛불을 다루지 않지만 맵 데이터에는 들어간다.
- **3번 — 유령 시작 타일과 키 배치.** 시작 타일은 createState·테스트에 필수. 키 배치: 2장 표는 "방향키"라고 적었으나 3번은 키 배치를 미정으로 둔다 → 방향키 외 키(예: 다른 키 조합)가 있는지, 아니면 방향키만으로 확정인지 사람이 정리해야 한다. 이 계획은 2장 표에 적힌 방향키만 쓴다.
- **9번 — 8색 팔레트 값.** sprites.js·화면 색의 전제.
- **11번 — AGENTS.md가 가리키는 5·6장과 충돌 여부 확인.** 4·5·6장 채운 직후 확인.

R1 구현과 별개로 R1 **완료 판정**에 필요한 항목:
- **10번 — 수용 기준 번호 체계** (9장, R2 예정). 이것 없이는 R1 완료 선언 불가.

목록 1~11에 없지만 R1에 필요한 미정 항목 (기획서 공백):
- **A. 이동 차단 규칙:** 유령이 벽 칸이나 맵 가장자리 밖으로 이동하려 할 때의 결과. (8번은 "벽이 시야를 막는지"이며 이동 차단은 다루지 않음.) 4장에서 정해야 함.
- **B. 2장 (에이전트 제안) 값 확정:** 한 칸 이동 시간 120 ms, 타일 16×16 px, 화면 320×240 px(20×15 타일). 확정 전에는 canvas 크기·스프라이트 크기·맵 그리드 크기·이동 애니메이션을 정할 수 없다.

R1에 필요 없는 항목: 4번(시간 초과 점수), 5번(경비병 턴 동기), 6번(시야 방향), 7번(같은/인접 타일 판정 순서), 8번(벽이 시야를 막는지) — 모두 경비병·점수·패배 관련으로 R1 범위 밖.

## 7. Verification

수용 기준 번호는 **9장 확정 후 채운다.** 아래 절차의 "[9장 번호]" 자리는 그때 기입한다.

### 자동
- `node --test test/` — test/logic.test.js, test/levels.test.js 전부 통과.
- 정적 확인(사람 또는 리뷰어): `src/logic.js` 에 `canvas`, `document`, `window` 참조 없음; 저장소에 `package.json`·이미지·오디오 파일 없음; 6장 외 hex 색 없음; UI 문구가 strings.js 밖에 없음; 5장 그리드와 levels.js 문자열이 한 글자도 다르지 않음.

### 사람이 브라우저에서 확인 [9장 번호: 9장 확정 후 기입]
1. 저장소 루트에서 `python3 -m http.server 8000` 실행 후 브라우저로 `http://localhost:8000/` 연다 (또는 index.html 직접 열기가 되면 그 방법).
2. 5장 레이아웃 1의 벽·바닥(및 맵에 있는 정적 타일)이 6장 팔레트 색으로 그려진 것을 본다. 5장 문서와 화면 배치를 눈으로 대조한다.
3. 유령이 5장 시작 타일에 있는지 본다.
4. 방향키 위/아래/왼쪽/오른쪽을 각각 한 번 눌러, 누를 때마다 유령이 해당 방향으로 정확히 한 칸 움직이는지 본다. 키를 누르지 않으면 움직이지 않는지 본다 (턴제, 스펙 R11).
5. 벽 쪽·가장자리 쪽으로 눌러 4장에서 확정한 규칙대로 동작하는지 본다 (규칙 확정 전이면 이 단계는 보류로 기록).
6. 개발자 도구 콘솔에 오류가 없는지, 네트워크 탭에 외부 요청이 없는지 본다.
- fixture 데이터 스크린샷은 증거가 아니다. 실제 5장 데이터로 확인한다.

### 리스크와 대응
- 4·5·6장 및 (에이전트 제안) 값이 확정되지 않으면 R1 코드 착수 불가 → 0단계를 막힘 항목으로 보고하고 멈춘다.
